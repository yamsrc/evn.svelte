# Agent Instructions

## Architecture

Before making any changes to the codebase, **always refer to `architecture.md`** for:

- Domain organization patterns and structure
- Layer responsibilities and conventions
- Component organization (domain vs shared components)
- Forms pattern and service connectors
- Linked entities pattern
- Other architectural guidelines

Understanding the architecture is essential for maintaining code quality and consistency.

## Internationalization (i18n)

This project uses the `svintl` package for internationalization. When working with i18n:

- **Use `svintl` for all internationalization needs** - This is the standard i18n solution for this project
- **Read the package documentation** - For detailed usage instructions, refer to the `svintl` package README
- **⚠️ Important: Avoid using `sync` command** - The `sync` command should only be used in emergency situations, as it places a very heavy load on the AI API and is time-consuming. Use alternative methods for managing translations when possible.
- **Do not update generated intl files directly** - Files generated by `svintl` should not be edited manually. Use the appropriate `svintl` commands and workflows instead. Generated files include:
  - `built.js` files (auto-generated dictionary files)
  - `types.ts` files (auto-generated TypeScript definitions)
  - `*.yaml` files in `intl/` directories (translation files)

## Svelte

When working with Svelte code:

- **Use `$effect` only as a last resort** - Having `$effect` in code indicates a bad architectural solution that leads to bugs and unexpected behaviors. Always prefer reactive declarations (`$:`), proper state management, and declarative patterns over `$effect`. If you find yourself reaching for `$effect`, reconsider the architecture and find a more declarative solution.
